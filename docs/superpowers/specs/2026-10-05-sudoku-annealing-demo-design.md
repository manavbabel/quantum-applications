# Sudoku annealing demo: design

Date: 2026-10-05

## Purpose

An interactive demo of quantum annealing for the NQCC stand at New Scientist
Live, the week after this spec. Visitors, from age 7 up, solve a sudoku against
the clock, watch an annealer settle the same puzzle as a thermometer is dragged
from hot to cold, then send the puzzle to a D-Wave quantum annealer and watch
it come back. Solve times go on a whiteboard by hand, so the app has no
leaderboard.

It succeeds if:

- it runs on an ordinary Windows 11 laptop that has Python, with a mouse or a
  touchscreen
- the 9x9 annealing view animates smoothly (60 fps on a typical laptop)
- a visitor never sees an error: if D-Wave can't be reached, the recorded
  simulation result appears in its place
- what's shown is real: the annealing view replays a recorded simulated
  quantum annealing run, and the qubit, coupler and energy figures come from
  the actual problem

## Running it

```
git clone https://github.com/manavbabel/quantum-applications.git
cd quantum-applications/sudoku/demo
python setup_dwave.py
python serve.py
```

`setup_dwave.py` is run once, with internet, before the event. `serve.py`
starts a local server and opens the page in the default browser; F11 makes it
full screen. Opening `index.html` directly also works, but then "Send to
quantum annealer" always shows the recorded simulation.

## Puzzles

Five puzzles per size, one chosen at random each time a size is picked:

| size | difficulty | starting target |
|---|---|---|
| 4x4 | medium | 10 blanks |
| 6x6 | medium | 22 blanks |
| 9x9 | easy | 40 blanks, solvable by naked singles alone |

`precompute.py` makes them with `random_puzzle` under a fixed global seed and
keeps only puzzles with exactly one solution (a small backtracking counter).
With one solution, "follows the rules" and "matches the solution" are the same
check. The blank counts are starting points: they come down if the simulation
fails to solve a puzzle reliably or the D-Wave check (below) shows a low
success rate.

## Screens

The layout is landscape, from 1366x768 up. Every screen after the first has a
Back button.
Fonts are ones Windows already has, so nothing needs downloading: Segoe UI for
clues and labels, and Segoe Print for anything handwritten (the visitor's
entries and pencil marks). The grid looks like paper, with thick lines around
the boxes.

### 1. Pick a size

Three large buttons: 4x4, 6x6, 9x9.

### 2. Solve it

- The grid is blurred until Start is pressed; then a timer counts up in
  seconds with one decimal place.
- Click or tap a cell, then a number on the on-screen pad (1 to n, plus an
  erase key). Keyboard digits, arrow keys, Backspace and Delete also work.
- A cell turns red when its number clashes with another in its row, column or
  box. A wrong number with no clash stays uncoloured, as on paper.
- The timer stops when the grid is full with nothing red. The time is shown
  large, with "Write your time on the board!".
- Buttons: "Anneal it", "New puzzle".

The visitor can press "Anneal it" without solving.

### 3. Anneal

1. Every blank cell fills with pencil marks for all n numbers, in a small grid
   (2x2 for 4x4, 2x3 for 6x6, 3x3 for 9x9). The numbers already used in the
   cell's row, column or box are struck through and fade, over about 1.5 s.
   This is the classical step the encoding does before annealing.
2. A vertical thermometer beside the grid starts at HOT. Dragging it down, or
   pressing "Anneal" (which lowers it over about 6 s), plays the recording
   forward; dragging it back up plays it backward.
3. At each position:
   - each pencil mark's size and opacity follow the recorded probability of
     that number in that cell
   - the marks jitter, with an amplitude proportional to the temperature
   - each cell's background goes from warm red to white with its recorded
     share of broken rules
4. At COLD, each cell's mark grows into a full-size digit, a green ripple runs
   across the grid from the top-left corner, and "Solved!" appears.
5. Button: "Send to quantum annealer".

The slider is labelled as temperature, as decided on 2026-10-05. In the
simulation it controls the transverse field; the simulation's temperature is
fixed.

### 4. Send to quantum annealer

A list of the five stages sits beside the animation, each ticked off in turn.
Every stage stays on screen for at least 2.5 s.

1. Formulating the problem: each blank cell splits into a column of dots, one
   qubit per remaining candidate, and lines join qubits that share a rule.
   Counters show the real numbers of qubits and couplers.
2. Mapping to physical qubits: the chip's qubit lattice is drawn faintly, and
   the puzzle's qubits light up chain by chain. Counters show the number of
   physical qubits and the longest chain.
3. Sending the problem: a pulse travels down into a drawing of the chip's
   refrigerator, beside a thermometer reading 0.015 K, "colder than outer
   space". This stage lasts until the reply arrives.
4. Processing results: the 100 reads drop into a histogram of energies. The
   bar at zero lights up, with "x of 100 answers broke no rules".
5. Done: the lowest-energy read fills the grid cell by cell. Any wrong cells go
   red, with a caption along the lines of "Today's quantum computers still make
   mistakes on bigger problems" (final wording to agree).

A 6px dot in the bottom-right corner tells staff where the last result came
from: filled for D-Wave, hollow for the recorded simulation.

## Animation and performance

- Only `transform` and `opacity` are animated, so the browser composites them
  on the GPU. A 9x9 has at most 729 pencil marks.
- The jitter is one CSS keyframe animation with a random delay per mark; its
  amplitude is a CSS custom property on the grid, set from the slider, so no
  JavaScript runs per mark per frame.
- Slider positions between recorded frames are interpolated linearly.
- The chip lattice is drawn once to a canvas; only the highlights are redrawn.

## Data (`data.js`)

`precompute.py` writes one line, `window.DEMO = <json>;`, which the page loads
with a script tag (so it works when `index.html` is opened from disk) and
`serve.py` reads by taking the JSON between `=` and the final `;`.

- `chip`: solver name and region, the working qubits with drawing coordinates
  (from `dwave.graphs`' Pegasus or Zephyr layout), and the working couplers
- `puzzles`: for each size, five entries holding
  - `grid` and `solution`
  - `variables`: the `(r, c, v)` of each logical qubit, in a fixed order
  - `groups`: the "exactly one" groups as lists of variable indices, which
    give both the energy and the lines drawn in stage 1
  - `frames`: about 80 frames, each with the probability of every variable
    (its share of the 16 Trotter slices set to 1) and the broken-rule share of
    every blank cell
  - `qpu`: the chains (one list of physical qubits per variable), the physical
    Ising problem `h` and `J`, chain strength, `num_reads` (100) and
    `annealing_time`
  - `fallback`: the energies of 100 simulated annealing reads and the best
    read

How `precompute.py` fills it:

- Recordings: run `_sqa_read` with the default settings and `record_every`
  chosen to give about 80 frames, trying seeds in order until the read ends at
  energy 0. Seeds come from the global RNG.
- Chip mappings: fetch the solver's properties (free), find an embedding with
  `minorminer.find_embedding` under a fixed seed, set chain strength with
  `uniform_torque_compensation` (what `EmbeddingComposite` uses), and embed
  the BQM to get `h` and `J`.
- Fallback: `anneal_sqa(bqm, num_reads=100)`.
- `--qpu-check` (only with approval): sends each of the 15 puzzles once and
  prints the share of reads that solved it. Estimated cost 15 jobs of 100
  reads, about 0.5 to 0.75 s of QPU time.

## The server (`serve.py`)

Standard library `http.server` on `localhost:8765`, opening the page with
`webbrowser`. If it isn't running inside `sudoku/demo/.venv` and that venv
exists, it re-runs itself with the venv's Python and exits with its return
code, so nobody has to activate anything. Without the venv it still serves the
page, and `/api/status` reports that live runs are off.

- `GET /api/status` returns `{"live": true|false}`. Live means
  `dwave-cloud-client` imports, `dwave.conf` exists and the solver in
  `data.js` answered. The result is cached for 30 s.
- `POST /api/sample` with `{"size": 9, "index": 2}` calls
  `solver.sample_ising(h, J, num_reads=100, annealing_time=..., label="nqcc-sudoku-demo")`,
  expands the answer by `num_occurrences`, reads each chain back by majority
  vote (a tie gives 0), computes each read's energy from `groups`, and returns
  `{"source": "dwave", "energies": [...], "best": [...], "qpu_access_time": ...}`.
  Any exception returns HTTP 503.

The page checks `/api/status` on load and every 30 s. When it's live, stage 3
waits for `/api/sample`, giving up after 20 s. In every other case (opened from
disk, no token, network down, timeout, 503) it uses `fallback` and the staff
dot goes hollow.

## Setup (`setup_dwave.py`)

Standard library only. It can be re-run safely.

1. Create `sudoku/demo/.venv` if it's missing.
2. Install `requirements.txt` with the venv's pip.
3. If there's no `dwave.conf`, ask for the API token (from the Leap
   dashboard) and write:

   ```
   [defaults]
   token = ...
   region = <region from data.js>
   ```

   `dwave-cloud-client` reads `./dwave.conf` ahead of the user-wide config, so
   the token stays in this folder and the laptop's own D-Wave settings are
   untouched. Both scripts change to their own folder on start, so they work
   from any working directory.
4. With the venv's Python, connect and fetch the solver named in `data.js`
   (free), then check every chain's qubits and couplers are still working on
   it. Print `[OK]` or `[FAIL]` for each step, in ASCII.

If a mapping no longer fits, the fix is to re-run `precompute.py` on a machine
with the repo's uv environment and pull the new `data.js`.

## Testing

`test_demo.py`, run with `uv run pytest sudoku`:

- majority-vote readback on made-up chains, including a tie and a broken chain
- energies from `groups` match `build_bqm(...).energies` on random bit strings
- for every puzzle in `data.js`: exactly one solution, `solution` passes
  `is_solution`, the last frame rounds to the solution, the fallback's best
  read decodes to the solution, and every chain is connected and covers each
  logical coupler on the stored chip graph (`dwave.embedding.verify_embedding`)
- the server, with the D-Wave call swapped for a fake, returns the right shape
  from `/api/sample`, and returns 503 when the fake raises

By hand, in Chrome and Edge:

- every screen, with `index.html` opened from disk and through `serve.py`
- at 1366x768 and 1920x1080, with the mouse and with touch emulation
- the 9x9 annealing view in the DevTools performance panel, holding 60 fps
- one live D-Wave job of 100 reads (about 0.05 s of QPU time), only after
  approval

## Cost on the day

At about 0.14 s of QPU time per 1000 reads (measured on Advantage_system4,
2026-10-02), each press uses roughly 0.03 to 0.05 s, so 1,000 presses come to
under a minute.
